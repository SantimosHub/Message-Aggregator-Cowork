# Bitrix24 Message Aggregator (на платформе Битрикс24 Вайбкод)

Приложение для Битрикс24, которое собирает **все** входящие сообщения сотрудника с нескольких **внешних** порталов Битрикс24 и дублирует их в чаты на **основном** портале — в один **общий чат «Сборщик сообщений»** (на все порталы) или в **отдельный чат** «Сборщик сообщений: {Название портала}» на каждый портал — по выбору сотрудника при подключении. Связь односторонняя (только чтение, без ответа во внешний портал).

Полная история изменений — в [CHANGELOG.md](CHANGELOG.md). Журнал ведётся независимо от git-коммитов.

Приложение разрабатывается через **Битрикс24 Вайбкод** ([vibecode.bitrix24.tech](https://vibecode.bitrix24.tech)) — платформу, которая даёт AI-агенту (Claude Code, Cursor, Codex и т.д.) единый API, документацию и инфраструктуру для написания и деплоя приложений Битрикс24.

---

## 1. Идея и сценарий использования

У пользователей есть один «основной» портал Битрикс24, где работает несколько сотрудников, и у каждого сотрудника — свой набор «внешних» порталов (например, порталы клиентов, партнёров, подрядчиков), где ему тоже иногда пишут.

Вместо того чтобы логиниться в каждый портал отдельно и проверять сообщения, каждый сотрудник:

1. Открывает приложение на **основном** портале (оно уже установлено один раз на весь портал, встраивается прямо в интерфейс Битрикс24).
2. Через интерфейс приложения добавляет **свои** внешние порталы, с которых нужно забирать сообщения.
3. При подключении портала сотрудник выбирает, куда пересылать сообщения:
   - в **общий чат «Сборщик сообщений»** — один чат на все подключённые порталы (создаётся при первом подключении, переиспользуется для остальных);
   - или в **отдельный чат «Сборщик сообщений: {Название портала}»** — свой чат на каждый портал.
   Чат создаётся на основном портале и видим только этому сотруднику (и тем, кого он добавит в чат).
4. Все входящие сообщения, приходящие сотруднику на внешнем портале, автоматически дублируются в соответствующий чат основного портала — без фильтрации по диалогам, целиком.

Связь односторонняя: сообщения только читаются с внешнего портала и попадают в чат основного; отправка ответа из чата основного портала обратно во внешний портал не предусмотрена.

## 2. Как работает авторизация в Вайбкод (важно!)

Логин и пароль пользователя **нигде не используются и не хранятся** — ни Битрикс24 REST API, ни API Вайбкод так не работают.

Для **основного** портала используется только один вариант — ключ Вайбкод:

| Ключ | Где используется | Зачем |
|---|---|---|
| **`vibe_app_...`** (ключ авторизации, OAuth) | На **основном** портале | Даёт приложению встроиться в интерфейс Битрикс24 (пункт меню / виджет) и создавать чаты и сообщения от имени пользователя, который открыл приложение |

Для **внешних** порталов в приложении используется **единственный способ авторизации — входящий вебхук Битрикс24**. Способ через личный ключ Вайбкод (`vibe_api_...`) был в ходе разработки убран: он не был проверен вживую и не позволял узнать ID сотрудника на внешнем портале для пометки его собственных сообщений прочитанными (см. `external_portal_client.py`).

| Способ | Что это | Плюсы |
|---|---|---|
| **Входящий вебхук Битрикс24** | Стандартный вебхук, выпускается в самом Битрикс24: **Профиль → Ещё → Разработчикам → Другое → Входящий вебхук** | Есть на любом портале Битрикс24 без привязки к Вайбкод, настраивается за минуту, права можно ограничить точечно (`im`, `imopenlines`, `user`) |

> **Примечание о канале запросов.** Запросы к внешнему порталу по вебхуку идут напрямую в REST API Битрикс24 по URL вебхука (в обход Vibe API), поэтому вызовы для такого портала написаны отдельно. На внешнем портале платформа Вайбкод не требуется.

### Как это выглядит для пользователя на практике

Для **основного** портала:
1. Зайти на [vibecode.bitrix24.tech](https://vibecode.bitrix24.tech), войти через свой Битрикс24.
2. В разделе **Ключи авторизации** создать ключ `vibe_app_...` со скоупами `im`, `user` (для чтения профиля) и `placement`, режим доступа — **«Чтение и запись»** (нужен для создания чатов и отправки сообщений).
3. Этот ключ передаётся AI-агенту при разработке — именно он превращает приложение во встроенный в портал виджет.

> **Важный нюанс про `vibe_app_...`.** Сам по себе этот ключ не даёт доступа к write-операциям без пользовательской сессии: и `POST /v1/infra/servers` (создание сервера для деплоя), и `POST /v1/placements/bind` (встраивание виджета) требуют заголовок `Authorization: Bearer <vibe_session_...>`, который получают через одноразовый OAuth-флоу (`GET /v1/oauth/authorize` → `POST /v1/oauth/token`) от лица администратора портала. Это разовая настройка при разработке/деплое — обычные сотрудники после этого открывают виджет уже без всякого ручного OAuth: Gateway сам подставляет им `X-Vibe-Authorization: Bearer vibe_session_...` при открытии placement. Поэтому на практике:
> - **создание/деплой сервера backend** удобнее делать **личным ключом** (`vibe_api_...`) — он не требует сессии;
> - **регистрацию placement** (`placements/bind`) агент делает один раз через `vibe_app_...` + сессионный токен, полученный вручную через OAuth-флоу.

Для **каждого внешнего** портала — входящий вебхук:
1. На внешнем портале зайти в **Профиль → Ещё → Разработчикам → Другое → Входящий вебхук**.
2. Выбрать права **«Чат и уведомления (im)»**, **«Открытые линии (imopenlines)»** и **«Пользователи (user)»**, нажать **«Создать»**. Право `user` нужно, чтобы приложение показывало имена коллег-операторов, пишущих в открытую линию (`user.get`).
3. Скопировать URL вида `https://portal.bitrix24.ru/rest/12345/xxxxxxxxxxxxxx/` (целиком, вместе со слэшем на конце) и вставить его в UI приложения.

> **Зачем нужен `imopenlines`.** Сотруднику может писать не только напрямую, но и через **открытую линию** (Open Lines) — чат с клиентом, где сотрудник выступает оператором. Обычный `im.dialog.messages.get` технически доступен участнику чата, но не даёт надёжного доступа к истории сессии открытой линии (передача другому оператору, статус завершения и т.п.) — для этого нужны специальные методы (`imopenlines.dialog.get`, `imopenlines.session.history.get`), которые требуют отдельный скоуп `imopenlines`. Поэтому backend при опросе внешнего портала должен проверять оба источника: обычные диалоги (`im.recent.get` → `im.dialog.messages.get`) и чаты открытых линий (`imopenlines.dialog.get` → `imopenlines.session.history.get`), объединяя результат в единый поток сообщений для чата на основном портале.

Таким образом, никаких паролей — только выпущенные официальным способом ключи или вебхуки с ограниченными правами, которые можно в любой момент отозвать.

> И ключ `vibe_api_...`, и вебхук работают от лица того, кто их создал, — то есть от имени самого пользователя, поэтому «увидят» именно те сообщения, которые адресованы ему.

       ┌─────────────┼─────────────────────┐
       ▼              ▼                    ▼

**Основной** портал: виджет и определение личности работают через ключ авторизации
`vibe_app_...`, а **фоновые** операции (создание чата, отправка сообщений) — через
личный ключ `VIBE_BACKGROUND_API_KEY` на Бот-платформе (`imbot.v2.*`). **Внешние**
порталы подключаются **только вебхуком**: backend обращается напрямую к обычному
REST API Битрикс24 (`https://portal.bitrix24.ru/rest/.../метод.json`) этим URL
(способ `vibe_api` для внешних порталов был убран — он не позволял определить ID
сотрудника на внешнем портале и не был проверен вживую).

## 4. Компоненты системы

### 4.1. Встроенный виджет на основном портале
- Работает через **ключ авторизации** `vibe_app_...`, встраивается в портал через `POST /v1/placements/bind` (доступные места — `GET /v1/placements/available`). Ключ выпускается один раз на весь портал (администратором), а не отдельно на каждого сотрудника. **`placements/bind` требует также `Authorization: Bearer <session>`** — сессионный токен получается один раз через OAuth-флоу (`GET /v1/oauth/authorize` → `POST /v1/oauth/token`) от лица администратора; это разовый шаг настройки, не касается обычных сотрудников.
- Приложение — многопользовательское: каждый сотрудник открывает виджет внутри Битрикс24 без отдельного логина — Gateway Вайбкод сам передаёт серверу приложения, кто именно открыл виджет (заголовок `X-Vibe-Authorization` содержит ID текущего пользователя портала). Благодаря этому один и тот же `vibe_app_...` ключ обслуживает всех сотрудников сразу — заводить каждому свой ключ не требуется.
- Каждый сотрудник видит и настраивает **только свои** внешние порталы (фильтрация по `owner_user_id` в БД) и свои чаты.
- Интерфейс:
  - список подключённых внешних порталов текущего сотрудника и статус синхронизации по каждому,
  - форма добавления нового внешнего портала: **название портала** (для отображения, «Название портала» вместо «Домена») + **выбор чата** («Общий чат» / «Отдельный чат», см. раздел 1) + **URL вебхука**,
  - кнопка отключения/удаления портала — с предупреждением (двухшаговая кнопка + браузерный `confirm()`), что связанный с порталом чат будет удалён.
   - кнопка **«Сброс настроек»** в правом нижнем углу — массовый сброс: отключает **все** порталы сотрудника (независимо от статуса) и удаляет все чаты, созданные приложением (включая общий чат «Сборщик сообщений»); перед удалением — `confirm()` с подтверждением.
   - **уведомления об ошибках очистки**: если фоновое удаление чата при отключении портала или сбросе не удалось, виджет показывает явный banner с сообщением (читается через `GET /api/portals/notices`, очищается после показа через `DELETE /api/portals/notices`).
   - **Диагностика**: отдельная страница `/debug` показывает трассу последнего цикла опроса каждого портала (какие диалоги/линии видит опрос, сколько входящих переслал, какой курсор), статус портала, а также «пульс» фонового поллера и ошибки опроса — без доступа к логам платформы.
   - HTML виджета отдаётся с `Cache-Control: no-cache`, чтобы после деплоя не показывать старый интерфейс из кэша.

### 4.2. Backend на сервере Black Hole
[Black Hole](https://vibecode.bitrix24.tech/blackhole) — облачный сервер Вайбкод без публичного IP, доступ к которому идёт через защищённый туннель платформы. Подходит для нашего сценария, потому что приложению нужны:
- фоновая cron-задача (регулярный опрос внешних порталов),
- хранилище пар «внешний портал → ключ → chat_id»,
- обработчик HTTP-запросов от виджета (сохранение/удаление ключей).

Backend:
1. Принимает от виджета название портала + URL вебхука + выбранный `chat_mode` (`shared` / `separate`).
2. Проверяет учётные данные вызовом метода `profile` напрямую по URL вебхука (убеждаемся, что вебхук рабочий и отвечает).
3. Создаёт (или переиспользует) чат на основном портале:
   - `shared` — общий чат «Сборщик сообщений» (один на сотрудника; создаётся при первом подключении, дальше переиспользуется);
   - `separate` — отдельный чат «Сборщик сообщений: {Название портала}» на каждый портал.
   Чат создаётся через Бот-платформу (`imbot.v2.*`) и сохраняется как `main_chat_id`.
4. По расписанию (например, раз в 45 секунд) для каждого активного внешнего портала опрашивает новые сообщения прямым вызовом REST-методов Битрикс24 по URL вебхука (`im.recent.list` → `im.dialog.messages.get` для обычных диалогов, `im.recent.list` → `imopenlines.session.history.get` для чатов открытых линий).
5. Новые сообщения форматирует в **человеко-понятный дайджест** (портал, название чата, отправитель, время, текст; несколько сообщений одного чата объединяются в один дайджест) и отправляет в `main_chat_id` на основном портале через Бот-платформу.
6. Сохраняет курсор последнего обработанного сообщения, чтобы не дублировать при следующем опросе.
7. При отключении портала (`DELETE /api/portals/{id}`):
   - `separate` — удаляет отдельный чат портала на основном портале;
   - если это был последний портал сотрудника — удаляет и общий чат «Сборщик сообщений».
   Само удаление чата на основном портале делается через Бот-платформу: у прямого метода «удалить чат» нет, поэтому по очереди исключаются все участники-люди (`imbot.v2.Chat.User.delete`) и бот выходит из чата (`imbot.v2.Chat.leave`) — пустой чат исчезает автоматически. Удаление идёт отдельной фоновой задачей (не блокирует ответ 204).

> **Имена отправителей и «спящие» диалоги.** У чата открытой линии в истории (`imopenlines.session.history.get`) нет отдельных полей автора, кроме числового `senderid`, — имя отправителя берётся в приоритете: из объекта `users` того же ответа (имя сотрудника или клиента-коннектора), из префикса в начале текста («Имя: текст» или «Имя (телефон)\nтекст»), из названия диалога (`imopenlines.dialog.get` → `name`, где часто фигурирует имя из лида/контакта), либо остаётся нейтральное «Клиент». Поле `users` в ответах `im.*` на разных порталах приходит и словарём, и списком — приложение нормализует оба варианта. Чтобы подхватывать «спящие» непрочитанные диалоги (куда сообщения пришли, пока пользователь не заходил на портал), `im.recent.list` вызывается с `UNREAD_ONLY=Y` и подстраховывается счётчиками `im.counters.get` (включая `LINES`); при первом появлении диалога пересылаются только непрочитанные входящие, а не вся история. В `/debug` для каждого пересланного сообщения открытой линии видно, из какого источника взялось имя (разбивка по полям) — это помогает разбирать случаи, когда имя не подставилось.

> **Важно про курсор при разных `auth_type`.** Формат ответа и пагинация у `im.recent.get`/`im.dialog.messages.get` одинаковые независимо от того, идёт вызов через Vibe API или напрямую по вебхуку (Vibe API лишь проксирует тот же REST-метод Битрикс24), поэтому `last_message_cursor` можно хранить в едином формате для обоих `auth_type` — id последнего сообщения по каждому диалогу (или `DATE_CREATE`, если `im.recent.get` не даёт монотонного id). Раз сотруднику может одновременно писать несколько диалогов на одном внешнем портале, курсор должен быть не одним значением на портал, а **картой `dialog_id → last_message_id`**, иначе часть сообщений в параллельных диалогах будет теряться или дублироваться.

### 4.3. Хранилище данных
Можно использовать обычную БД на самом Black Hole сервере (SQLite/Postgres — по возможностям тарифа), либо [Хранилище файлов Вайбкод](https://vibecode.bitrix24.tech/docs/storage) для простых конфигов. **Подтверждено практикой (документация деплоя galaxy-приложений, раздел `BUILD`):** файловая система galaxy-контейнера **эфемерна между редеплоями** — при каждом деплое происходит `stop -> clean -> extract`, и всё вне специального пути **не переживает передеплой**. Персистентные данные обязаны лежать в примонтированном томе **`/data`** — только этот путь сохраняется между деплоями. Поэтому для MVP берём **SQLite**, но файл базы обязательно кладём по пути `/data/app.db` (не в рабочую директорию приложения), иначе база будет обнуляться при каждом обновлении кода. Минимальная схема:

**external_portals**
| поле | тип | описание |
|---|---|---|
| id | int | PK |
| owner_user_id | int | пользователь основного портала, добавивший запись |
| domain | string | домен внешнего портала (для отображения) |
| auth_type | enum | `webhook` — единственный способ авторизации внешнего портала (vibe_api убран) |
| credentials | string (encrypted) | URL вебхука (шифруется) |
| main_chat_id | int | ID чата на основном портале для этого внешнего портала |
| chat_mode | enum | `shared` \| `separate` — куда пересылать: общий чат «Сборщик сообщений» или отдельный чат портала |
| last_message_cursor | json | карта `{dialog_id: last_message_id}` — курсор последнего обработанного сообщения по каждому диалогу внешнего портала (не одно значение на весь портал, т.к. диалогов может быть несколько одновременно) |
| status | enum | `connecting` \| `active` \| `error` \| `disabled` |
| created_at | datetime | |

Ключ `vibe_app_...` основного портала хранится отдельно — в переменных окружения сервера Black Hole, не в базе.

**shared_chats** — записи общих чатов «Сборщик сообщений» (один на сотрудника):
| поле | тип | описание |
|---|---|---|
| owner_user_id | int | сотрудник (PK, уникальный) |
| chat_id | int | ID общего чата на основном портале |
| title | string | название общего чата («Сборщик сообщений») |
| created_at | datetime | |

## 5. Основной сценарий работы

1. Пользователь открывает виджет приложения на основном портале (встроен через `vibe_app_...`).
2. Добавляет внешний портал: указывает название портала, выбирает «Общий чат» или «Отдельный чат» и вставляет URL вебхука, ранее полученный на этом внешнем портале.
3. Backend проверяет учётные данные (вызов `profile` по URL вебхука), создаёт (или переиспользует) чат на основном портале, сохраняет запись в БД вместе с `chat_mode`.
4. Cron-задача на Black Hole каждые N секунд обходит все активные записи `external_portals` и запрашивает новые сообщения пользователя на каждом внешнем портале напрямую через REST API Битрикс24 (по URL вебхука).
5. Найденные новые сообщения пересылаются человеко-понятным дайджестом в `main_chat_id` на основном портале через Бот-платформу.
6. Курсор обновляется, статус синхронизации отображается в виджете.
7. При отключении портала связанный с ним чат удаляется (отдельный — всегда; общий — если портал был последним), с предварительным предупреждением в виджете.

## 6. Как поручить это AI-агенту (Вайбкод-промпт)

Разработка ведётся в диалоге с AI-агентом (Claude Code, Cursor, Codex — любой инструмент, умеющий читать документацию, писать код и выполнять команды в проекте). Агент сам вызовет `GET /v1/me`, получит доступные методы и права ключа и напишет код — читать документацию по методам REST API Битрикс24 вручную не нужно.

Пример стартового промпта:

```
Создай приложение для Битрикс24 с авторизацией на платформе Битрикс24 Вайбкод.

Приложение встраивается в основной портал как виджет (ключ vibe_app_xxx выпускается
один раз на весь портал). Приложением пользуются несколько сотрудников одновременно —
каждый видит и настраивает только свои внешние порталы и свои чаты (разграничение по
ID текущего пользователя, который Gateway Вайбкод передаёт в заголовке при открытии
виджета).

Каждый сотрудник добавляет свои внешние порталы Битрикс24, указывая домен и
**входящий вебхук** (URL вида `https://portal.bitrix24.ru/rest/ID/TOKEN/`) —
единственный способ авторизации внешнего портала (личный ключ `vibe_api` был
убран). Запросы к внешнему порталу идут напрямую в REST API Битрикс24
стандартными методами `im.recent.get` / `im.dialog.messages.get` /
`imopenlines.session.history.get`.

Для каждого добавленного внешнего портала приложение создаёт отдельный чат на
основном портале, видимый только этому сотруднику.

Забираются ВСЕ входящие сообщения сотруднику на внешнем портале, без фильтрации по
диалогам. Связь односторонняя — только чтение, ответ из чата основного портала во
внешний портал не отправляется.

Раз в ~45 секунд фоновая задача опрашивает каждый внешний портал по его вебхуку
на новые входящие сообщения и пересылает их в соответствующий чат основного
портала (через Бот-платформу Вайбкода `imbot.v2.*`). Ожидаемое количество
внешних порталов — 4-10 на одного сотрудника, реального времени не требуется.

Разверни серверную часть на сервере Black Hole (нужны cron-задача и хранение
пар портал/ключ/chat_id/owner_user_id).

Ключ авторизации основного портала: vibe_app_xxx (виджет/личность),
+ фоновые операции — личный ключ VIBE_BACKGROUND_API_KEY (скоуп imbot).
Документация: https://vibecode.bitrix24.tech/v1/me
```

После получения общего каркаса можно уточнять детали в отдельных запросах: формат сообщений в чате, обработку ошибок протухшего ключа, UI списка порталов и т.д.

## 7. Технологический стек

- **Backend:** Python (FastAPI) — зафиксировано.
- **БД:** SQLite (для MVP) или PostgreSQL — решение зависит от того, эфемерна ли ФС Black Hole (см. раздел 4.3).

## 8. Безопасность

- Логины и пароли не запрашиваются и не хранятся ни в каком виде — только ключи Вайбкод или вебхуки с ограниченными правами.
- Вебхуки внешних порталов создаются **только** с правами `im`, `imopenlines` и `user` — этого достаточно для чтения обычных диалогов, чатов открытых линий и имён сотрудников; лишние права (например, `crm`, `disk`) добавлять не нужно.
- И ключ, и вебхук/`credentials` хранятся в БД **в зашифрованном виде** (одинаково, независимо от `auth_type`).
- Ключ `vibe_app_...` основного портала хранится в переменных окружения сервера Black Hole, не в БД и не в коде.
- Ключи Вайбкод можно ограничить списком разрешённых IP и конечным сроком действия; вебхуки такого встроенного ограничения по IP не имеют — единственная защита это секретность самого URL, поэтому URL вебхука нужно передавать только через защищённый канал (форму в самом приложении) и никогда не публиковать в логах, чатах, репозиториях.
- Если ключ или вебхук скомпрометирован — он отзывается (в личном кабинете Вайбкод для ключа, или удаляется в настройках вебхуков Битрикс24 для вебхука), создаётся новый, обновляется в конфиге приложения.
- Сервер Black Hole не имеет публичного IP — доступ к бэкенду идёт только через туннель платформы, что снижает риск внешних атак на сам сервер.

## 9. Ограничения платформы, которые нужно учитывать

- **Лимит REST API Битрикс24** (общий для всех запросов к внешнему порталу по вебхуку): ~10 запросов в секунду на портал.
- Для вебхуков можно использовать стандартный батч-метод REST API Битрикс24 (`batch`) для сокращения числа вызовов.
- **Расчёт под целевую нагрузку:** у каждого сотрудника до 4–10 внешних порталов; при нескольких сотрудниках общее число подключений на всём основном портале может доходить до нескольких десятков. При поллинге раз в 30–60 секунд и объединении вызовов в батчи это укладывается в лимиты с большим запасом (даже 50 подключений при опросе раз в 30 сек — это ~1,7 запроса/сек в среднем на всё приложение). Если число подключений вырастет на порядок — можно перейти на менее частый опрос для неактивных порталов (адаптивный интервал) вместо фиксированных 30–60 сек для всех.
- Фоновые операции на **основном** портале (создание чата, отправка сообщений) идут личным ключом `VIBE_BACKGROUND_API_KEY` (`vibe_api_...`, скоуп `imbot`) через Бот-платформу Вайбкода. Это снимает вопрос об истечении 24-часового сессионного токена `vibe_app_...`: фоновым вызовам cron-задачи не нужна открытая сессия сотрудника в браузере. `vibe_app_...` остаётся для встраивания виджета и определения личности через Gateway.

## 10. Этапы разработки (roadmap)

1. **MVP:** многопользовательский виджет на основном портале (`vibe_app_...`, один раз на весь портал) + форма добавления внешнего портала (название + выбор общего/отдельного чата + URL вебхука) + поллинг всех входящих сообщений раз в 30–60 секунд с сервера Black Hole.
2. **v1.1:** обработка ошибок (просроченный/отозванный ключ или вебхук внешнего портала), уведомление сотрудника в интерфейсе. Важно: ошибка одного `external_portals`-подключения (протухший ключ, невалидный вебхук, `403`) не должна прерывать цикл опроса остальных подключений в том же тике cron — каждый портал обрабатывается независимо (try/catch на уровне записи), а не общим batch-запросом на всех сразу; статус конкретной записи переводится в `error`, остальные продолжают опрашиваться штатно.
3. **v1.2 (опционально, по запросу):** переход на обработчики событий вместо поллинга — рассматривать только если 30–60 сек перестанет устраивать; для MVP не требуется.
4. **v2.0 (опционально, по запросу):** фильтрация сообщений по конкретным диалогам, двусторонняя связь (ответ из основного портала во внешний), статистика по порталам — не входит в текущий объём, добавляется только если появится такая потребность.

## 11. Зафиксированные решения по проекту

| Вопрос | Решение |
|---|---|
| Какие сообщения забирать с внешнего портала? | Все входящие сообщения сотруднику, без фильтрации по диалогам/чатам |
| Нужна ли двусторонняя связь? | Нет, только чтение — ответ из чата основного портала во внешний не отправляется |
| Сколько внешних порталов подключаем? | 4–10 на сотрудника (заложен запас в расчёте лимитов, см. раздел 9) |
| Один пользователь основного портала или несколько? | Несколько сотрудников — приложение многопользовательское, каждый видит и настраивает только свои внешние порталы (см. раздел 4.1) |
| Куда пересылать сообщения? | По выбору при подключении: общий чат «Сборщик сообщений» (один на все порталы) или отдельный чат «Сборщик сообщений: {Название портала}» (см. раздел 1) |
| Что с чатом при отключении портала? | Отдельный чат портала удаляется; если портал был последним — удаляется и общий чат. Перед удалением — предупреждение в виджете |
| Есть ли «сброс настроек»? | Да: кнопка «Сброс настроек» отключает все порталы сотрудника и удаляет все чаты приложения (отдельные + общий) с подтверждением (см. описание в разделе 4.1) |
| Поллинг или реальное время? | Поллинг раз в 30–60 секунд — этого достаточно, переход на события не требуется |

Эти решения уже учтены во всех разделах README выше. Если что-то из этого изменится в процессе разработки (например, вырастет число подключаемых порталов на порядок или понадобится двусторонняя связь) — соответствующие разделы (9, 10) стоит пересмотреть.

## 12. Локальный запуск, деплой и регистрация виджета

### Локальный запуск (без Битрикс24)

```bash
cd server
python -m venv .venv && source .venv/bin/activate   # или свой способ управления окружением
pip install -r requirements.txt
cp .env.example .env   # и заполнить VIBE_APP_KEY
uvicorn app.main:app --reload
```

- `GET /health` — 200 всегда, без авторизации.
- `GET /api/me` — вернёт 401 без заголовка `X-Vibe-Authorization` (это нормально: этот заголовок
  подставляет Gateway, когда приложение открыто как placement за Black Hole; локально без
  деплоя его взять неоткуда).

### Деплой на Black Hole (galaxy app)

Выполняется **локально у разработчика** — доступ к `vibecode.bitrix24.tech` нужен реальный,
из песочницы AI-агента он недоступен.

```bash
cd server
export VIBE_API_KEY=vibe_api_...   # ЛИЧНЫЙ ключ, скоуп vibe:infra (НЕ vibe_app_...!)
export DEPLOY_SERVER_ID=<ID_сервера>   # редеплой существующего сервера; без него скрипт создаст НОВОЕ приложение
python -m scripts.deploy_backend
```

Скрипт сам:
1. Проверит ключ и его скоупы через `GET /v1/me`.
2. Спросит у платформы список рантаймов и подберёт подходящий для Python (либо попросит
   задать `DEPLOY_RUNTIME=...` вручную, если не определит сам).
3. Соберёт архив исходников (без `.env`, `__pycache__` и т.п.) и задеплоит galaxy-приложение.
4. Дождётся поднятия сервера и покажет публичный URL — это и есть `APP_BASE_URL` для `.env`.

Перед сборкой архива скрипт **автоматически поднимает версию приложения на 0.01**
(`scripts/bump_version.py` → `server/version.txt`, 1.20 → 1.21 → 1.22 …). Версия из
`version.txt` подставляется сервером в виджет (плейсхолдер `__APP_VERSION__`) и
показывается внизу по центру — то есть после каждого деплоя она растёт на 0.01.

Скрипт печатает **сырые ответы API на каждом шаге** — если платформа ответит не так, как мы
ожидали (другие названия полей, другой формат рантаймов), это будет сразу видно, и мы поправим
скрипт по факту вместо того, чтобы гадать по документации.

### Разовая регистрация виджета (после первого успешного деплоя)

```bash
cd server
# в .env должны быть заполнены VIBE_APP_KEY и APP_BASE_URL (из вывода деплоя выше)
python -m scripts.bind_placement
```

Интерактивный скрипт проведёт через OAuth-вход администратора основного портала и
зарегистрирует виджет (`LEFT_MENU`) через `POST /v1/placements/bind`. Это разовая операция —
после неё сотрудники открывают виджет уже без ручного OAuth.
