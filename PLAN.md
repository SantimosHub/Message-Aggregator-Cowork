## Этап 0. Подготовка окружения

- [x] Зарегистрироваться на [vibecode.bitrix24.tech](https://vibecode.bitrix24.tech), войти под основным порталом (**bot24.bitrix24.ru**).
- [x] Выпустить ключ `vibe_app_...` (скоупы `im`, `user`, `placement`, режим «Чтение и запись») — проверен через `GET /v1/me`, платформа подтвердила тип `oauth_app`.
- [x] Выпустить личный ключ `vibe_api_...` — изначально планировался для тестового внешнего портала, но окажется полезен и для деплоя backend (см. ниже).

> **Важно про роли ключей (выяснено на практике через `GET /v1/me`):** `vibe_app_...` без пользовательской сессии не может создавать сервер (`POST /v1/infra/servers`) и не может забиндить placement (`POST /v1/placements/bind`) — оба требуют `Authorization: Bearer <vibe_session_...>`. Поэтому: **деплой backend делаем личным ключом** `vibe_api_...` (не требует сессии), а **bind виджета** — ключом `vibe_app_...` + сессионным токеном, полученным один раз вручную через OAuth-флоу (см. Этап 1).

- [x] Выпустить (или переиспользовать) ключ/вебхук для **одного тестового внешнего** портала: используем вебхук `b24-7ao7mn.bitrix24.ru`, скоупы `im`, `imopenlines`, `user` — проверено вызовом `scope.json`.
- [ ] Уточнить у платформы Black Hole, сохраняется ли файловая система между рестартами (см. правку в README, раздел 4.3) — от ответа зависит выбор БД. *(можно выяснить прямо в процессе Этапа 1/2 — не блокирует старт кода)*
- [x] Определить стек: **Python (FastAPI)** — зафиксировано.
- [x] Создать репозиторий проекта, базовую структуру папок (`/server`, `/widget`, `/db`).

**Результат этапа:** ✅ есть все ключи, стек выбран, репозиторий создан — Этап 0 завершён.

**Результат этапа:** ✅ виджет виден в левом меню основного портала (bot24.bitrix24.ru), backend различает пользователей через Gateway-сессию.

> **Важные уроки этого этапа (см. подробности в истории чата/сводке контекста):**
> - Смена «управляющего ключа» сервера деактивирует OAuth-ключ, которым он раньше управлялся — никогда так не делать для рабочего ключа.
> - `handler` в `placements/bind` должен быть `https://vibecode.bitrix24.tech/v1/bitrix-handler` (платформенный), а не наш собственный URL — иначе зацикливание на логине. Пофикшено в `bind_placement.py`.
> - Мастер «Опубликовать приложение» на платформе создаёт Standalone VM (где рантайм `python311` нестабилен) — надёжнее создавать Galaxy-сервер напрямую через `deploy_backend.py`, а затем через «Редактировать» переключить URL опубликованного ключа на него.
> - Доступ к серверу («Доступ») по умолчанию «Только владелец» — обязательно переключать на «Весь портал» для многопользовательского сценария.
> - Временные диагностические эндпоинты `/api/debug/headers` и `/api/debug/key-check` были добавлены для отладки и **удалены** после подтверждения работоспособности.

> `deploy_backend.py` уже пробрасывает `DATABASE_URL` и `CREDENTIALS_ENCRYPTION_KEY` в контейнер (был предусмотрен заранее в списке `ENV_VARS_TO_FORWARD`).

## Этап 3. Backend: подключение внешнего портала ✅ ЗАВЕРШЁН

- [x] Эндпоинт приёма от виджета: домен + `auth_type` (`vibe_api` | `webhook`) + credentials. *(`POST /api/portals`, `server/app/routes/portals.py`)*

  - `webhook` → вызов `profile.json` напрямую по URL.
  *(`server/app/external_portal_client.py`; заодно есть `check_webhook_scope()` через `scope.json`, пригодится для будущей UI-диагностики)*
- [x] При успехе — создание чата на основном портале через Vibe API (`vibe_app_...`), сохранение `main_chat_id`. *(`create_group_chat()` в `vibe_client.py` — `POST /v1/chats`, только `X-Api-Key`, без сессии — подтверждено документацией платформы во время разработки Этапа 3)*
- [x] Сохранение записи в `external_portals` со статусом `active`.
- [x] Обработка невалидных credentials — понятная ошибка в ответ виджету (без падения сервера). *(400 с текстом ошибки; невалидный портал не попадает в БД — проверено тестом)*

**Результат этапа:** ✅ подтверждено e2e smoke-тестом (с моками внешних вызовов): через `POST /api/portals` можно подключить внешний портал любым из двух способов, чат создаётся автоматически, credentials никогда не возвращаются клиенту, невалидные данные не роняют сервер и не попадают в БД. Также добавлены `GET /api/portals` (список своих порталов) и `DELETE /api/portals/{id}` (с проверкой владельца) — не требовались явно по плану, но тривиальны и полезны для тестирования до появления UI (Этап 6).

> Реальный API-метод создания чата — `POST /v1/chats {title, users: [ids]}` (im.chat.add), отправка — `POST /v1/chats/chat{id}/messages {message}` (im.message.add). Полный контракт документации `imChat` найден и задокументирован в процессе (см. историю чата) — платформа предоставляет отдельный раздел `imChat` для этого, а не Entity API.

## Этап 4. Cron-задача опроса внешних порталов ✅ РЕАЛИЗОВАНО (требует проверки на живом vibe_api-портале)

- [x] Планировщик — простой asyncio-таск, запускается в `startup` event FastAPI, корректно отменяется в `shutdown` (без APScheduler — осознанное решение). *(`server/app/poller.py`, `POLL_INTERVAL_SECONDS = 45`)*
- [x] Для каждой активной записи `external_portals` — независимая обработка, ошибка одной не прерывает остальные (порталы опрашиваются параллельно через `asyncio.gather`). *(`_process_portal()` в `poller.py`, покрыто тестом на изоляцию ошибок)*
- [x] Запрос новых сообщений — оба источника одновременно, обычные диалоги (`im.recent.list` → `im.dialog.messages.get`) и открытые линии (`im.recent.list` → `imopenlines.session.history.get`, определяется по полю `lines` в ответе). *(`server/app/external_message_fetcher.py`)*
  - `webhook` → напрямую REST Битрикс24, синхронный `requests` в потоке (обходной путь вокруг Gateway-бага, см. `external_portal_client.py`) — контракт подтверждён официальной документацией Битрикс24 REST.
  - `vibe_api` → `POST /v1/batch` — **контракт НЕ проверен вживую**, реализация следует стандартному формату batch Битрикс24 по аналогии с уже подтверждёнными вызовами `/v1/chats`. **Обязательно проверить на реальном vibe_api-портале перед Этапом 7**, поправить `_vibe_batch_call()` в `external_message_fetcher.py` при расхождении.
- [x] Обновление курсора (`dialog_id → last_message_id`) по каждому диалогу отдельно, при первом появлении диалога история не подтягивается (запоминается стартовая точка, чтобы не заспамить чат старыми сообщениями при подключении портала).
- [x] При ошибке авторизации (протухший/отозванный ключ) — перевод статуса записи в `error`, лог причины. *(`ExternalPortalApiError.is_auth_error`)*
- [x] Тесты логики курсора/парсинга/изоляции ошибок (сеть замокана). *(`server/tests/test_stage4_poller.py`)*

**Результат этапа:** сервер регулярно опрашивает все подключённые внешние порталы, не теряя и не дублируя сообщения. Пересылка сообщений в чат основного портала — пока заглушка-лог (`_handle_new_messages` в `poller.py`), реальная отправка появится на Этапе 5.

> ⚠️ Перед тем как считать Этап 4 полностью завершённым: проверить `_vibe_batch_call` на реальном vibe_api-портале (Этап 0 уже выпустил тестовый вебхук-портал, но не vibe_api-портал — понадобится дополнительный тестовый ключ). До этой проверки webhook-путь можно считать production-ready, vibe_api-путь — черновым.

## Этап 5. Пересылка сообщений в чат основного портала ✅ РЕАЛИЗОВАНО

- [x] Форматирование сообщения: автор, время, текст, ссылка на диалог во внешнем портале. *(`_format_digest()` в `server/app/poller.py`)* — ссылка вида `/online/?IM_DIALOG={dialog_id}` собрана по распространённому в сообществе паттерну Битрикс24, официальной REST-документацией не подтверждена — проверить на Этапе 7.
- [x] Отправка в `main_chat_id` через Vibe API ключом `vibe_app_...` (`vibe_client.send_chat_message`, уже подтверждён рабочим на Этапе 3).
- [x] Батчинг: все новые сообщения одного диалога за один цикл опроса объединяются в ОДНО сообщение чата — снижает нагрузку на лимит 300 запросов/мин `vibe_app_...` с большим запасом (см. расчёт в README, раздел 9).
- [x] Идемпотентность: курсор диалога продвигается **только после успешной отправки**. Если отправка дайджеста упала — курсор диалога откатывается к последнему подтверждённому значению, сообщения переотправятся на следующем цикле опроса. Ошибка отправки одного диалога не мешает доставке остальных (диалоги обрабатываются независимо, как и порталы на Этапе 4).
- [x] Тесты: форматирование (порядок сообщений всегда хронологический независимо от порядка ответа Битрикс24), батчинг по диалогам, откат курсора при неудачной отправке, в т.ч. частичный откат при нескольких диалогах. *(`server/tests/test_stage5_forwarding.py`)*

**Результат этапа:** новые сообщения из внешнего портала появляются в чате основного портала с задержкой не более 30–60 сек (интервал опроса), без дублей и без потерь при временных сбоях отправки.

> ⚠️ Не проверено вживую: точный формат ссылки на диалог (`/online/?IM_DIALOG=...`) и то, как ссылка ведёт себя для диалогов открытых линий (структура `dialog_id` для них тоже под вопросом — см. предупреждение в Этапе 4 про `vibe_api` batch). Проверить вместе на Этапе 7.

## Как будем работать по этому плану

- Если в процессе что-то из «Зафиксированных решений» (README, раздел 11) меняется — сначала правим README, потом продолжаем по плану.
